# 互联网产品（非 AI）简历修改 Skill 参考规范 · 执行层

> 本文件是互联网产品（非 AI）岗位的 **执行层**：判断岗位子族、选择证据、改写、真实性校验。
>
> **2026-09-25 拆分说明**：本文件与 `internet-product-证据依据.md`（依据层）共同构成互联网产品岗位参考。依据层提供证据强度、过度声称边界、措辞与动词、国内样本结论（§8）；本执行层负责结构化判断与改写。AI 类岗位另见 `ai-执行规范.md` / `ai-证据依据.md`，本文件不覆盖 AI 专属岗位。
>
> 用法：先用本文件的结构化规则做岗位子族判定与证据选择，再按需查 `internet-product-证据依据.md`（证据强度、过度声称边界、措辞与动词、国内样本结论）。

---

## 0. 文档用途与使用边界

### 0.1 这份文档用于什么

本文件用于帮助简历修改/生成 Skill 完成以下任务：

1. 判断目标 JD 更接近 P1 / P2 / P3 / P4 中哪一类互联网产品岗位（或混合）；
2. 判断该岗位最需要哪些 Hiring Signals；
3. 从候选人真实经历中寻找对应 Evidence；
4. 决定哪些项目和事实应优先展示、弱化或保留；
5. 在不虚构候选人经历的前提下，把事实改写成更符合目标岗位的简历表达；
6. 校验产品/增长/平台/商业化表述是否与候选人真实职责与结果匹配。

### 0.2 这份文档不用于什么

本文件不是候选人的事实来源，不得用市场研究内容替代候选人真实经历。

不得因为市场上常见某项能力，就自动给候选人补写：

- 0→1 从零搭建
- 主导 / 负责（当事实只支持参与时）
- 增长结果（DAU / 留存 / GMV / ROI 等，无基线无结果不得写）
- 商业化 / 营收指标
- 平台架构 / API / SDK 设计（未真实负责时）
- 客户成功 / 续费 / ARR / NRR（B2B 岗未真实接触时）
- A/B 实验 / 数据体系（未真实设计时）
- 跨部门 owner 身份

### 0.3 信息优先级

当信息冲突时，Skill 按以下优先级处理：

**P0 候选人明确提供的事实与原始简历**
↓  
**P1 用户提供的目标 JD**
↓  
**P2 本文档的岗位级规则与市场研究结论**
↓  
**P3 通用简历写作常识**

说明：

- 候选人事实决定“能不能写”；
- 目标 JD 决定“优先写什么”；
- 本文档决定“哪些事实通常构成有效招聘信号”；
- 本文档不能授权 Skill 创造候选人没有提供的事实。

# 1. 核心执行原则

## HARD-001｜事实不可扩写成不存在的能力

候选人没有明确提供的事实，不得自动升级。

例如：

- “使用 AI 工具写 PRD” ≠ “具备 AI 产品规划能力”
- “参与增长活动” ≠ “对增长指标负责”
- “做过需求文档” ≠ “主导产品策略”
- “协助项目落地” ≠ “独立 owner 一条业务线”
- “做过几次访谈” ≠ “建立了用户洞察体系”
- “提升体验” ≠ “有可验证的业务结果”

如果某个高价值事实缺失，应优先追问，而不是补写。

---

## HARD-002｜技能声明不能当作项目证据

以下内容默认只属于 **Skill Claim**：

- 熟悉 PRD / 原型设计
- 会使用 Axure / Figma / 墨刀
- 熟悉 SQL / 数据看板
- 了解 A/B 测试 / 增长黑客
- 熟悉 MVP / 敏捷
- 会使用 AI 工具提效

只有当候选人提供了具体行为、项目、结果或验证方式后，才可升级为 **Proven Capability**。

---

## HARD-003｜方法论与技术名词必须服务于真实产品事实

A/B 测试、MVP、增长黑客、漏斗分析、用户分层、RARRA、PLG、API、SDK、Serverless 等名词，只有在回答以下问题时才值得进入项目 bullet：

- 为什么采用这个机制/方法？
- 它解决了哪个用户/业务问题？
- 候选人本人做了什么？
- 如何验证是否有效？
- 最终改变了什么结果？

若名词只是关键词堆砌，应降低权重。

---

## HARD-004｜不把参与升级成负责，不伪装层级

本研究不支持“产品简历多写 owner / 主导 / 从 0 到 1 就更高级”的规则。

Skill 应根据目标岗位判断：

- P1/P2：优先看用户洞察、产品设计、数据驱动、跨职能交付与结果；
- P3：在平台/开发者产品中可强调抽象能力、API/SDK/能力治理、开发者效率指标；
- P4：在 B2B/SaaS 中可强调客户共创、GTM、商业化、续费/ROI、合规；
- 技术型/平台型 JD：只有在 JD 明确要求时，才显著提高架构/技术深度权重。

---

## HARD-005｜项目价值由完整证据链决定，不由“产品感”词汇密度决定

优先寻找：

**真实问题 → 用户/业务证据 → 产品决策或权衡 → 跨职能行动 → 交付物 → 可验证结果**

而不是：

**大量产品名词（MVP / 增长 / 数据驱动 / 用户中心）→ 无用户 → 无验证 → 无结果**

# 2. 目标岗位分类器

下游 Skill 不应仅根据岗位标题分类，应优先判断：

**工作对象 + 核心交付物 + KPI**

| Role ID | 目标岗位 | 主要工作对象 | 主要交付物 | 常见结果对象 |
|---|---|---|---|---|
| P1 | 核心用户产品 | 终端用户、内容/社区、交易体验 | 用户侧功能、PRD、原型、交互、交易链路 | 体验、活跃、留存、转化、GMV、满意度 |
| P2 | 增长产品 | 用户规模、漏斗、增长玩法 | 增长机制、裂变/激励、活动、转化链路 | DAU/MAU、拉新、激活、留存、复购、ROI |
| P3 | 平台 / 开发者产品 | 内部/外部开发者、平台能力、系统 | API/SDK、能力治理、可复用底座、开发者工具 | 接入效率、复用率、活跃开发者、调用成功率 |
| P4 | 企业 / B2B SaaS | 企业客户、业务线、售前/客户成功 | 企业软件、商业化方案、GTM、交付 | ARR、NRR、续费、客户采用、ROI、合规 |

### ROLE-CLASSIFY-01

若 JD 直接负责用户侧功能、交易链路、社区/内容体验、端到端购物/消费体验，优先归 P1。

### ROLE-CLASSIFY-02

若 JD 高频出现拉新、激活、留存、转化、裂变、漏斗、AARRR/RARRA、增长玩法、用户激励，优先归 P2。

### ROLE-CLASSIFY-03

若 JD 高频出现 API、SDK、开放平台、开发者、中后台、基础设施、能力治理、可复用底座、生态，优先归 P3。

### ROLE-CLASSIFY-04

若 JD 的最终 KPI 是 ARR、续费、NRR、客户采用、商机、商业化、合规，且服务对象是企业客户/业务线，优先归 P4。

### ROLE-CLASSIFY-05

“增长”不是充分分类条件。同样是增长：
- 用户增长产品 owner 可以属于 P2；
- 平台增长（行业/产业带增长）可以属于 P3；
- 海外营销云增长可以属于 P4；
- 用增长手段改善交易/留存的产品策略岗可能属于 P1。

# 3. 四类岗位的简历修改目标

## P1｜核心用户产品

### 优先寻找的 Hiring Signals

1. 用户/场景问题识别
2. 用户洞察（访谈 / 行为数据 / 同理心）
3. 产品判断与权衡
4. 需求优先级与 MVP 范围
5. 交易/转化链路设计
6. 数据驱动迭代
7. Ownership
8. 跨职能交付
9. 体验与业务结果

### 优先展示的 Evidence

- 真实用户侧功能 / 交易链路 / 社区或内容产品设计
- 用户洞察驱动的产品决策（从发现到落地）
- 从问题定义到上线的完整闭环
- 体验与转化指标（如转化率、GMV、留存、活跃）
- 用 AI 工具提效的真实案例（仅当真实存在）

### 不应强行补的内容

- 增长玩法（裂变/激励体系）除非真实负责
- 平台架构 / API 设计
- 商业化营收指标
- 大模型/Agent 能力（除非目标 JD 明确要求且候选人真实具备）

---

## P2｜增长产品

### 优先寻找的 Hiring Signals

1. 增长模型理解（AARRR / RARRA）
2. 漏斗诊断与归因
3. 增长玩法设计（裂变 / 激励 / 活动 / 补贴）
4. 实验与 A/B 测试
5. 数据分析与复盘
6. 用户分层与生命周期
7. Ownership（对增长指标负责）
8. 产品抽象（一次性活动 → 可复用增长能力）
9. 跨团队推进

### 优先展示的 Evidence

- 拉新 / 激活 / 留存 / 复购 / 转化链路优化
- 增长玩法与激励机制（券 / 权益 / 任务 / 分享）
- A/B 实验、漏斗分析、归因分析
- 从玩法设计、产品方案、实验上线到效果复盘的闭环
- 可复用的增长产品能力沉淀（可配置 / 可规模化）
- 真实增长指标（如裂变系数、换端转化、首单转化、ROI）

### 不应强行补的内容

- 把“参与了一次活动”写成“对 DAU/GMV 负责”
- 没有实验/数据支撑的“显著提升”
- 平台架构、B2B 商业化、客户续费

---

## P3｜平台 / 开发者产品

### 优先寻找的 Hiring Signals

1. 平台抽象能力（从具体场景抽象通用能力/流程/数据模型）
2. 开发者体验（接入 / 调试 / 调用 / 运维效率）
3. API / SDK / 能力治理（注册 / 版本 / 权限 / 审计）
4. 可复用底座与工具市场
5. 技术理解与跨团队协作（研发 / 运维 / 架构）
6. 开发者效率指标（接入周期 / 调用成功率 / 复用率 / 活跃开发者）
7. 生态与商业化（如适用）
8. Ownership

### 优先展示的 Evidence

- 统一开发者入口 / 工具体系 / 能力治理机制
- 把业务场景沉淀为可复用平台能力
- 开发者效率指标改善
- 与研发/运维/架构协作落地
- 平台商业化/生态（如真实存在）

### 不应强行补的内容

- 工程实现细节或代码（除非技术平台 JD 明确要求）
- C 端用户增长指标（除非该平台真的面向终端用户）
- 客户续费 / ARR（那是 P4 的结果对象）

---

## P4｜企业 / B2B SaaS 产品

### 优先寻找的 Hiring Signals

1. 客户共创与需求洞察
2. 复杂企业需求转化为可落地方案
3. 产品规划 / 路线图 / PRD / 用户故事 / 验收标准
4. GTM 与商业化（定价 / 套餐 / 销售赋能）
5. 客户成功与采用（签约 / 上线 / 续费 / NRR）
6. 合规与安全（SSO / 权限 / 数据驻留 / 审计）
7. 跨团队（销售 / 售前 / 客户成功 / 研发）推进
8. Ownership（对产品结果与商业指标负责）

### 优先展示的 Evidence

- 客户共创与行业/业务痛点诊断
- 从需求到上线的企业软件交付
- 商业化链路与定价/GTM 设计
- 重点客户签约/上线/续费或最佳实践沉淀
- 合规与安全设计（如真实涉及）
- 商业结果（ARR / NRR / 续费 / 客户数 / ROI）

### 不应强行补的内容

- 终端用户增长/C 端体验指标
- 平台技术架构（除非是 PaaS/开发者平台）
- 把“售前支持”写成“产品 ownership”

# 4. 产品能力深度校准

> 本模型用于简历内容校准，不是公司官方职级。

| Level | 定义 | 可观察证据 | Skill 处理方式 |
|---|---|---|---|
| P0 用户/业务基础 | 能理解用户/业务问题，做需求分析与功能设计 | 用户访谈、需求文档、原型、PRD | 任何产品岗的基础信号 |
| P1 数据 / 实验驱动 | 能用数据发现问题、设计并解读 A/B 实验、做漏斗/归因 | SQL/看板、实验设计、指标定义 | 对 P1/P2 是强差异化信号 |
| P2 平台 / 技术理解 | 理解 API/SDK/架构/系统约束，能与研发对齐方案 | 平台抽象、能力治理、技术方案评审 | 对 P3 与复杂 B2B 提高权重 |
| P3 商业化 / 跨域 | 理解商业模式、定价/GTM、客户成功、跨团队 owner | 商业化设计、续费/ARR、售前协作 | 对 P4 与高级岗提高权重 |
| P4 战略 / 生态 | 组合管理、平台生态、长期路线图、组织影响 | 战略取舍、生态构建、业务线 owner | 仅在高级/负责人 JD 明确需要时强调 |

### TECH-01

不要因为候选人不会写代码而自动降低 P1/P2/P4 的整体匹配判断。

### TECH-02

不要因为候选人会 SQL/原型就自动判断其具备产品 ownership。

### TECH-03

对非技术候选人，优先寻找：

**真实用户/业务问题 → 产品方案 → 数据/实验验证 → 跨职能交付 → 结果**

而不是通过堆砌增长/平台/商业化名词制造专业感。

# 5. Hiring Signal → Evidence 解释规则

| Signal | 弱证据 | 中等证据 | 强证据 |
|---|---|---|---|
| 用户洞察 | “做过访谈” | 访谈/行为数据后形成需求 | 多源用户证据改变产品判断，并由行为/指标验证 |
| 产品判断 | “负责需求” | 做竞品/优先级排序 | 从用户行为发现高价值问题，做关键取舍并产生结果 |
| 0→1 | “参与项目” | 负责某模块 MVP | 从问题定义、方案、构建到上线及结果全链路 owner |
| 数据驱动 | “熟悉数据分析” | 做看板/SQL | 数据发现问题 → 假设 → 实验 → 决策 → 结果 |
| 增长 / Adoption | “负责运营推广” | 活动带来试用 | 拉新→激活→留存→复购完整漏斗改善，有裂变系数/ROI |
| 跨职能交付 | “沟通协调” | 跟进项目落地 | 对齐多方围绕决策/交付，并承担结果 |
| 平台复用 | “了解平台” | 画流程图 | 把具体场景抽象为通用能力并实际被复用 |
| 商业化 / 客户成功 | “支持客户” | 参与签约/上线 | 设计定价/GTM、续费/NRR、客户采用并可验证 |
| Business Impact | “提升效率” | 有明确业务指标 | GMV/留存/转化/ROI 等有基线、结果和业务范围 |
| Ownership | “协助”“参与” | 独立负责功能 | 主动识别问题、做关键取舍、协调多团队并承担结果 |
| Scale | 一次性功能 | 小组试点 | 从单点复制到多业务/多客户/大规模用户并形成机制 |

### EVIDENCE-01

Skill 改写时应优先提高 **强证据** 的信息密度，而不是通过形容词强化弱证据。

### EVIDENCE-02

如果只有弱证据，应保守表达；不要把语气升级成“主导”“从 0 到 1”“显著提升”。

# 6. 候选人事实提取 Schema

Skill 在改写任何项目之前，优先从原始材料中提取以下字段。

```yaml
project:
  context: ""
  target_user_or_customer: ""
  problem: ""
  old_workflow: ""
  candidate_role: ""
  ownership_scope: ""
  key_decisions: []
  actions: []
  user_research:
    method: null        # 访谈/问卷/行为数据/竞品/桌面
    evidence: ""
  prioritization:
    framework: null     # 机会排序/ROI/价值矩阵/MVP范围
    trade_offs: ""
  experiment:
    type: null          # A/B/灰度/漏斗/留存分析/归因
    metric: ""
  launch_delivery: ""
  metrics:
    baseline: ""
    result: ""
    scale: ""
  adoption_or_growth: ""
  business_impact: ""
  platform_or_gtm: ""
  collaboration: []
  constraints: []
  evidence_status:
    explicit_facts: []
    missing_facts: []
```

### EXTRACT-01

`explicit_facts` 中的信息才允许直接进入最终简历。

### EXTRACT-02

`missing_facts` 中如果包含高价值信息，应优先生成追问，而不是自动补齐。

典型追问包括：

- 这个功能是全链路 owner 还是参与某一个环节？
- 有多少真实用户 / 客户使用？
- 你本人负责到哪一步？
- 是否做过 A/B 实验或数据验证？基线与结果分别是什么？
- 项目前后指标分别是多少？
- 是上线、试点还是方案？
- 是否接触商业化/客户续费/合规？
- 业务价值有没有可验证口径？

---

# 7. 项目选择与排序规则

## SELECT-01｜目标岗位优先

项目优先级由目标岗位决定，不存在统一的“用户产品一定排第一”。

### Target P1

优先顺序：

**真实用户/交易功能 > 用户洞察驱动的产品决策 > 强数据驱动项目 > 增长/平台项目 > 纯执行类需求**

### Target P2

优先顺序：

**增长闭环（拉新/激活/留存/转化）+ 实验/数据 > 强运营/活动项目 > 用户产品项目 > 纯执行类**

### Target P3

优先顺序：

**平台抽象/可复用能力 > 开发者效率改善 > 中后台/工具建设 > C 端增长项目**

### Target P4

优先顺序：

**客户共创 + 商业化 + 交付/续费 > B2B/SaaS 落地项目 > 通用产品项目 > 纯行业研究**

---

## SELECT-02｜传统项目不因“不是某子族”自动删除

若传统项目能够证明：

- 用户洞察
- 产品判断与优先级
- 0→1
- 数据驱动
- 跨职能交付
- 商业结果
- 复杂项目推进
- Ownership

则仍可作为对应产品岗的基础能力证据。

---

## SELECT-03｜小闭环项目可以高价值

当项目具备：

**真实问题 + 产品方案 + 数据/实验验证 + 迭代 + 用户/结果**

即使规模不大，也可在对应子族匹配时提高优先级。

# 8. Bullet 改写规则

## EDIT-01｜优先写“证据链”，不要求每条塞满所有元素

> **改写前硬门**：进入 Step 5/6 改写前，必须先读本族「改写措辞透镜」专节（位于 EDIT-05 之后），以其中动词表 / 装饰性标签规则 / 叙事链为唯一措辞依据；不得仅凭本 EDIT 规则或凭经验措辞。

推荐信息顺序：

**业务/用户问题 → 候选人动作/关键决策 → 产品机制/方法 → 验证 → 结果/规模**

根据事实完整度选择 3–5 个最强元素，不需要机械套模板。

---

## EDIT-02｜结果优于职责罗列

弱：

> 负责用户产品功能设计，与研发协作推进上线。

强：

> 针对 XX 用户在某交易环节的 XX 痛点，主导 XX 链路 redesign，通过 XX 实验/数据验证，最终改善 XX 转化率/GMV/留存。

只有原始材料支持的字段才能填入。

---

## EDIT-03｜方法/技术名词必须具体但不过度包装

好的表达应回答“为什么”和“如何影响产品”。

例如：

- “设计用户分层 + 权益激励体系以支持老客提频……”
- “将一次性增长活动抽象为可配置的活动模板，支撑多场景复用……”
- “建设统一开发者入口与 SDK/CLI，把接入周期从 X 降到 Y……”

而不是：

- “运用增长黑客思维”
- “基于数据驱动决策”
- “打造平台生态能力”

---

## EDIT-04｜Ownership 动词必须与事实匹配

可使用：

- 参与：候选人只是协作成员
- 负责：有明确责任范围
- 独立负责：有明确独立范围
- 主导：拥有关键决策与推进责任
- 从 0→1：从问题定义/方案到 MVP/上线确有完整参与

若原材料无法证明，不得升级动词。

---

## EDIT-05｜指标使用真实口径

若有基线和结果，优先写：

**from X → Y / +X% / -X% / 覆盖 N 用户 / N 客户 / N 场景**

若没有数字，可使用可验证的非数字结果：

- 上线
- 完成试点
- 被业务团队采用
- 覆盖多个流程
- 形成标准化方案/可复用模板

不得生成“显著提升”“大幅增长”等无法验证的结果。

---

# 9. 非技术 / 商科候选人校准

## 改写措辞透镜（写作透镜·上提必读）

> 本族写作透镜核心已从依据层（`internet-product-证据依据.md` §3 装饰性标签 / §5 叙事链 / §6 动词表）上提至此处。进入 Step 5/6 改写前**必须**以本节为唯一措辞依据，不再回查依据层；完整示例与低价值表达清单见依据层 §3/§5/§6/§7。

### 有含义表述 vs 装饰性标签
- **可写（仅当能解释底层工作时）**：用户洞察、需求优先级、MVP、A/B 测试、漏斗分析、归因、用户分层、增长玩法/激励、API/SDK/能力治理、开发者体验、平台复用、GTM、定价、客户成功、续费/ROI、合规（SSO/RBAC/数据驻留）、数据看板。
- **禁止当装饰标签贴**：`数据驱动`、`用户中心`、`增长黑客`、`平台生态`、`商业化`、`端到端产品生命周期`、`owner`、无实验与结果的 `A/B 测试`、无结果的 `GMV/DAU 增长`。
- **提醒**：方法论名词（如 A/B 测试、RARRA）不是能力本身，只有当候选人真的设计/解读了实验或增长闭环时才是证据。

### 动词表（按证据类型选词）
- 发现与框定：identified / investigated / synthesized / diagnosed / framed / validated
- 产品判断：defined / prioritized / sequenced / scoped / traded off / shaped
- 交付：prototyped / piloted / launched / shipped / instrumented / integrated / scaled
- 结果：improved / increased / reduced / accelerated / expanded / retained / enabled
- 增长/采用：activated / acquired / retained / converted / adopted / expanded
- 平台/生态：abstracted / standardized / enabled / generalized / exposed
- 商业化/客户：commercialized / priced / positioned / onboarded / renewed
- 用与事实匹配的动词。`owned / 负责` 意味着真正的决策责任，不只是参与。

### 叙事链（按子族选）
- **P1 核心用户产品**：用户/业务问题 → 用户洞察/证据 → 产品决策或权衡 → 跨职能交付 → 体验/转化结果
- **P2 增长产品**：增长问题/漏斗瓶颈 → 增长机制/玩法设计 → 实验/数据验证 → 采用/转化结果 → 可复用能力沉淀
- **P3 平台/开发者产品**：场景痛点 → 平台抽象/能力设计 → API/SDK/治理 → 开发者效率指标 → 复用/生态
- **P4 企业/B2B**：客户/业务问题 → 需求共创/方案 → GTM/商业化 → 交付/上线 → 采用/续费/ROI
- 最强经历第一条通常先立住「问题 + ownership + 结果」，不以通用职责开头；完整链路可跨多条 bullet 铺开。

---

## NONTECH-01｜不要伪装成工程师或增长黑客

对于商科、咨询、运营、内容背景，优先体现：

**用户/业务理解 × 产品判断 × 数据意识 × 跨职能推进 × 落地结果**

不要为了专业感强写：

- 平台架构
- 大模型/Agent（除非真实且目标 JD 要求）
- SDK/API 实现细节
- 复杂商业化模型

除非真实存在。

---

## NONTECH-02｜不同目标子族的补强方向

### Target P1

优先寻找：

**用户洞察 + 产品决策 + 数据/实验验证 + 体验或转化结果**

### Target P2

优先寻找：

**增长闭环 + 实验/数据 + 可复用增长能力 + ROI**

### Target P3

优先寻找：

**平台/流程抽象 + 可复用能力 + 开发者/业务效率结果**

### Target P4

优先寻找：

**客户共创 + 商业化/GTM + 交付/续费 + 业务结果**

---

## NONTECH-03｜不要把背景迁移自然度写成录取概率

原研究中的迁移自然度（如商科/运营 → P1/P2/P4 较顺，技术背景 → P3 较顺）仅表示既有能力复用程度，不代表录取概率。

# 10. JD 定制流程

下游 Skill 在有目标 JD 时，建议按以下顺序处理。

### STEP 1｜分类

将 JD 分类为 P1 / P2 / P3 / P4，可允许主类 + 次类。

例如：

`Primary = P2`
`Secondary = P1`

### STEP 2｜提取 JD Signals

从 JD 提取：

- Must
- Common
- Preferred
- 技术/数据深度
- KPI / 结果对象
- 用户/客户类型
- 业务场景

### STEP 3｜抽取候选人 Evidence

使用第 6 节 Schema，只记录明确事实。

### STEP 4｜建立匹配表

```yaml
signal_match:
  - signal: "增长闭环"
    evidence: "候选人原项目事实"
    strength: "strong | medium | weak | none"
  - signal: "用户洞察"
    evidence: ""
    strength: "none"
```

### STEP 5｜决定项目优先级

优先展示：

- 与目标 JD 高相关；
- Evidence 强；
- Candidate Ownership 清楚；
- 有结果或验证闭环的项目。

### STEP 6｜改写

执行第 8 节规则。

### STEP 7｜真实性 QA

检查是否出现：

- 新增不存在的技术栈/方法论
- 新增不存在的数字
- Ownership 升级
- 参与写成主导
- 方案写成上线
- 活动写成增长结果
- 技能词写成 Proven Capability

若出现，回退。

# 12. 研究结论的置信度与禁止外推

以下属于本研究较稳定、可供 Skill 直接参考的模式：

- 互联网产品不是统一岗位，应按工作对象、交付物和 KPI 分为 P1/P2/P3/P4；
- “会用 AI 工具”弱于真实用户洞察/产品设计/数据验证；
- 增长岗看重完整闭环（拉新→激活→留存→复购）与可复用能力，而非单次活动；
- 平台岗看重抽象能力与开发者效率，而非单纯功能交付；
- B2B/SaaS 看重客户共创、商业化与续费，而非仅功能上线；
- 项目应优先证明与目标岗位一致的真实结果函数；
- 非技术背景不等于不适合产品岗，但不得伪装成工程师或增长黑客。

以下不能被 Skill 当成硬规则：

- 所有产品 PM 都必须会写代码；
- 所有增长岗都必须会搭建增长系统；
- 某一家公司一定偏好某一种候选人；
- 本研究未充分覆盖的公司可以用其他公司的模式代替；
- 把“参与某业务”直接等同于“负责该产品线”。

---

# 13. 研究缺口

本研究自身已明确存在以下缺口，Skill 不应自行补齐：

1. 部分子族（尤其 P3 平台细分、P4 海外 SaaS）的完整 JD 数量少于理想配额；
2. 小米、百度、京东、快手、拼多多的近期完整产品 JD 样本覆盖不均；
3. 本研究主要是岗位类型与能力信号研究，不包含足够的职级/年限分层样本，因此不应从本文档推导 Senior/Lead/Principal 的统一规则；
4. 公开招聘页可能在职位关闭后重定向，应以原始 JD 与岗位标识作追溯。

# 14. 给下游 Skill 的最短决策规则

当上下文有限时，只保留以下逻辑：

> **先看目标 JD 属于 P1/P2/P3/P4 哪类，再从候选人事实中找对应 Hiring Signal 的强 Evidence。**

> **候选人事实决定能不能写；目标 JD 决定优先写什么；本文档决定什么通常算强证据。**

> **产品简历不是方法名词越多越好，而是“问题 → 证据 → 产品决策 → 跨职能行动 → 交付 → 可验证结果”越完整越好。**

> **非技术候选人不要伪装成工程师或增长黑客；优先证明用户/业务理解、产品判断、数据意识与落地结果。**

> **任何缺失的技术、指标、Ownership、上线状态和结果都不得自动补写。**
