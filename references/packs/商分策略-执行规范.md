## 0. 文档用途与使用边界

### 0.1 这份文档用于什么

本文件用于帮助简历修改 / 生成 Skill 完成以下任务：

1. 判断目标 JD 更接近四类子族（A 战略分析 / B 商业分析 / C 经营分析 / D 业务策略）中哪一类；
2. 判断该岗位最需要哪些 Hiring Signals；
3. 从候选人真实经历中寻找对应 Evidence；
4. 决定哪些项目 / 事实应优先展示、弱化或保留；
5. 在不虚构经历前提下，把事实改写成更符合目标岗位的简历表达；
6. 校验商分 / 策略表述是否与候选人真实责任深度匹配。

### 0.2 这份文档不用于什么

本文件不是候选人的事实来源，不得用市场研究内容替代候选人真实经历。

不得因为市场上常见某项能力，就自动给候选人补写：

- 策略 / 主导 / 操盘 / 闭环 / 数据驱动 / 商业敏感度 / 结果导向 / Owner 意识
- 战略（仅凭行业研究）
- 国际化商分能力（仅凭英语 / 留学）
- 经营结果 / 利润改善（无归因边界）
- 业务增长（无个人作用链）

### 0.3 信息优先级

**P0 候选人明确提供的事实与原始简历**
↓
**P1 用户提供的目标 JD**
↓
**P2 本文档的岗位级规则与市场研究结论**
↓
**P3 通用简历写作常识**

候选人事实决定“能不能写”；目标 JD 决定“优先写什么”；本文档决定“什么通常算强证据”。本文档不能授权 Skill 创造候选人未提供的事实。

## 1. 核心执行原则（HARD 规则）

### HARD-001｜事实不可扩写成不存在的能力

候选人没有明确提供的事实，不得自动升级。

- “参与分析” ≠ “独立定义问题”
- “提供数据” ≠ “完成商业分析”
- “制作报告” ≠ “形成商业判断”
- “完成行业研究” ≠ “制定战略”
- “提出建议” ≠ “制定完整策略”
- “策略获批” ≠ “推动策略落地”
- “推动项目” ≠ “对业务结果负责”
- “业务增长” ≠ “增长可归因于候选人”

若高价值事实缺失，应优先追问，而不是补写。完整 A≠B 边界见 §1.6。

---

### HARD-002｜标签 / 自我称谓不能当作证据

“数据驱动、商业敏感度、结果导向、Owner 意识、战略思维、strong communication”等元标签，以及“国际化视野”等无项目的修饰语，默认只算 Skill Claim，不构成 Evidence。只有当候选人提供了具体行为、决策、结果或验证方式后才可升级（等价表达见 §9 G1-2）。

---

### HARD-003｜三个“不要”

> **不要从岗位名称推能力；不要从动作推责任；不要从团队结果推个人归因。**

先找“问题—判断—决策 / 策略—执行—结果”的证据链，再决定候选人是什么类型、项目有多强、Bullet 可以用多强的动词。Title 只能触发进一步分类，不能直接决定岗位类型。

---

### HARD-004｜深度阶梯不可自动升级

动词强度必须跟随依据层 L0–L8 深度模型，不能高于候选人实际证据层级。

- L1–L2 跑了 SQL / 做了分析，不得写成“驱动、实现”；
- L2–L3 发现相关性，不得写成“识别因果”；
- L3–L4 做了 idea，不得写成“完成策略设计”；
- L4–L5 参与项目，不得写成“对业务结果负责”。

各子族强证据阈值不同：战略分析 L3–L4 且真实影响决策即可很强；商业分析通常 L3 以上；经营分析往往要 L6–L7；业务策略若只有 L2 数据执行则很弱，强证据通常 L4–L6 甚至 L7。详见依据层 §3 深度模型。

---

### HARD-005｜国际化 / 英文岗位：语言 ≠ 能力 + 语言能力硬规则

英语、小语种、留学只证明跨语言工作可行性或弱背景信号，不能单独升级成海外市场判断、本地化能力或商业分析能力。语言成绩应作为“门槛达标”事实（如雅思 7.0 / CET-6），不写成能力结论。

> ⚠️ **语言能力硬规则（读 profile，禁止硬编码）**：候选人的语言能力**只以 `profile.md` → `hard_prohibitions` 为准**。凡档案未明确记载的语言，一律不得写任何能力表述（包括"母语 / 流利 / 好 / 双语"）。海外校区 / 交换经历一律用"英语工作语言"描述，不得引申当地语言能力。【强制】

---

### HARD-006｜真实性边界 A ≠ B 规则（强制 hard guardrails）

下列“已知事实 A 不等于 B”是商业分析 / 策略简历最常见的夸大，必须作为硬性护栏，不是文风建议：

| 已知事实 A | **不等于** B |
|---|---|
| 参与分析 | ≠ 独立定义问题 |
| 提供数据 | ≠ 完成商业分析 |
| 制作报告 | ≠ 形成商业判断 |
| 完成行业研究 | ≠ 制定战略 |
| 支持战略规划 | ≠ 拥有战略规划责任 |
| 提出建议 | ≠ 制定完整策略 |
| 制定策略文档 | ≠ 策略获得决策通过 |
| 策略获批 | ≠ 推动策略落地 |
| 推动项目 | ≠ 对业务结果负责 |
| 跟踪指标 | ≠ 改善经营结果 |
| 参与预算 | ≠ 拥有资源配置权 |
| 向管理层汇报 | ≠ 影响管理层决策 |
| 熟练 SQL | ≠ 具备商业分析能力 |
| 处理大量数据 | ≠ 拥有商业洞察 |
| 搭建 Dashboard | ≠ 建立经营管理体系 |
| 发现相关性 | ≠ 识别因果关系 |
| 做出 idea | ≠ 完成策略设计 |
| 参与 OKR | ≠ 负责目标制定 |
| 项目上线 | ≠ 项目产生商业价值 |
| 业务增长 | ≠ 增长可归因于候选人 |
| 跨部门沟通 | ≠ 推动复杂利益相关方达成结果 |
| 参加 A/B 测试 | ≠ 自己设计实验或完成因果识别 |
| 做市场规模测算 | ≠ 得出可靠市场进入战略 |
| 做竞品分析 | ≠ 形成差异化竞争策略 |
| 降低成本 | ≠ 创造净商业价值，除非验证质量 / 体验没有被破坏 |
| 指标同比提升 | ≠ 候选人策略产生增量效果 |
| 负责专题 | ≠ 候选人拥有专题定义权 |
| 协助战略项目 | ≠ Ownership |
| 模型准确率提高 | ≠ 商业结果提高 |
| 完成战略 PPT | ≠ 建立可执行战略机制 |

## 2. 子族分类器（ROLE-CLASSIFY）

下游 Skill 不应仅根据岗位标题分类，应优先判断：

**工作对象 + 核心产出 + 决策对象 + 是否有目标 / 预算 / 资源责任 + 是否设计具体杠杆 + 是否推动执行 + 是否验证结果**

| Role ID | 子族 | 主要分析对象 | 核心产出 | 是否设计策略 / 杠杆 | 常见结果责任 |
|---|---|---|---|---|---|
| A | 战略分析 / 研究 | 外部市场、竞争、技术、业务组合 | 战略判断、选项、规划、专题 | 是，偏方向 / 选择 | 决策质量、战略项目，而非天然直接收入 |
| B | 商业分析 / 决策支持 | 某业务问题或机会 | 诊断、洞察、方案建议 | 经常，但未必拥有执行杠杆 | 问题解决、决策支持 |
| C | 经营分析 / 管理 | 整体经营状态 | 指标体系、目标拆解、预测、复盘、改善 | 是，常通过经营机制 | 目标达成、利润 / 成本 / 效率、经营健康度 |
| D | 业务策略 / 策略运营 | 特定业务杠杆 | 规则、政策、分层、激励、定价、供给 / 流量方案 | **核心责任** | 更常直接对策略效果或业务指标负责 |

### ROLE-CLASSIFY-01

若 JD 核心是从模糊战略议题 / 市场变化出发，产出战略判断、选项、业务规划或高层决策建议，优先归 A。战略 BP 可作为 A+C 混合标签。

### ROLE-CLASSIFY-02

若 JD 核心是从具体业务问题出发，产出诊断、洞察、决策建议，数据是解决业务问题的手段而非最终产品，优先归 B。

### ROLE-CLASSIFY-03

若 JD 核心是对目标 / KPI / 预算 / 预测 / 资源 / 经营复盘建立持续管理机制，优先归 C（弱版本可能只是数据分析，需复核）。

### ROLE-CLASSIFY-04

若 JD 核心是直接设计定价 / 流量 / 供给 / 补贴 / 商品 / 商户 / 销售 / 履约等杠杆并要求策略落地、测量和迭代，优先归 D。

### ROLE-CLASSIFY-05

若岗位名为 Strategy & Operations / 战略运营 / 商业化策略 / 增长策略 / 国际化商业分析，先按上述字段判定落点，再叠加场景标签——它们不是独立的一级类型。

### 分类器运行顺序

`分析对象 → 主要业务问题 → 核心产出 → 决策对象 → 是否有目标 / 预算 / 资源责任 → 是否设计具体杠杆 → 是否推动执行 → 是否验证结果`

只有当这些字段不足时，Title 才作为弱先验。

### Title → 检查字段映射（弱先验，非判定）

| 看到的 Title | 最先检查什么 | 可能真实落点 |
|---|---|---|
| 商业分析 / Business Analysis | 是否负责目标预算？是否只做诊断？是否直接控制策略杠杆？ | B、C、D，甚至 A |
| 经营分析 | 是否拥有目标、预算、资源、复盘机制，还是仅报表分析？ | C；弱版本可能只是数据分析 |
| 战略分析 / Strategy | 产出是研究报告，还是战略选择、规划、战略项目？ | A；部分 A+D 混合 |
| 策略运营 | 是否设计规则 / 机制，还是执行既定 SOP？ | D 或普通运营 |
| 经营策略 | 是经营管理机制还是具体业务策略？ | C/D |
| 战略 BP | 是否同时参与战略制定、目标拆解和跨部门治理？ | A+C 混合标签 |
| 商业化 / 增长 / 定价 / 销售 / 供给 / 履约 / 国际化 | 看其控制的具体决策与杠杆 | 通常为 D，场景标签 |

### 相邻岗位边界（判定用）

| 相邻岗位 | 真正区分点 |
|---|---|
| 数据分析 / BI | 首要产出通常是测量 / 分析能力；商分首要价值是业务问题判断与决策输入。但高级数据分析也能提出策略并推动落地，不能只用“是否提建议”区分。 |
| 数据科学 | 核心资产是算法 / 统计或决策模型本身；商分核心资产是商业判断。 |
| FP&A / 业务财务 | 财务岗主责任仍是财务规划 / 控制 / 报表；经营分析会跨越财务口径进入业务变量。 |
| 策略产品经理 | 产品经理拥有产品需求 / 机制 / 系统建设责任；策略岗从业务杠杆和经营结果出发，产品只是落地载体。 |
| 普通运营 | 更常执行既定机制；策略运营要设计分层 / 规则 / 政策 / 资源机制并有验证循环。 |
| 行业研究 | 研究本身可终止于认识世界；战略岗位要把研究转化为“所以公司应该选择什么”。 |
| 管理咨询 | 是服务模式 / 背景，不是企业内岗位闭环；进入企业后是否具备执行与结果责任必须重新验证。 |
| 投资 / Corp Dev | 最终决策是投资 / 并购 / 交易或资本配置，而非主营业务经营策略。 |
| 商务拓展 | 核心动作是获取客户 / 伙伴并达成交易；分析是手段而非主要产出。 |
| 销售运营 | 若主要管理 pipeline / 佣金 / 区域资源，是 Sales Ops；若扩展到公司级经营诊断与策略，可出现迁移。 |
| PMO | 核心是治理“项目如何完成”；商分核心是“公司 / 业务应该做什么、为什么”。 |
| CEO Office / 总经办 | 是组织位置，不是稳定职能类型；必须重新编码其实际工作闭环。 |

## 3. 四类子族的简历修改目标

### A｜战略分析 / 研究

**优先寻找的 Hiring Signals**：外部市场 / 竞品 / 技术 / 商业模式研究、战略选项与取舍、业务规划、高层决策支持、结构化思维。

**优先展示的 Evidence**：独立问题定义 → 内外部证据 → 明确战略取舍判断 → 影响决策 / 规划 / 战略项目。

**不应强行补的内容**：公司级资源权（除非真实存在）；把“完成行业研究”写成“制定战略”；把“参与战略规划”写成“拥有战略规划责任”。

---

### B｜商业分析 / 决策支持

**优先寻找的 Hiring Signals**：业务问题定义、结构化分析 / 假设拆解、根因 / 机会识别、可执行建议、决策采用。

**优先展示的 Evidence**：模糊重要问题 → 独立诊断 → 根因 / 机会 → 建议 → 业务采用 / 改善。

**不应强行补的内容**：经营目标 / 预算责任（除非真实存在）；把“SQL 工作量 / Dashboard 数量”当核心；把“发现相关性”写成“识别因果”。

---

### C｜经营分析 / 管理

**优先寻找的 Hiring Signals**：指标体系、目标 / 预算拆解、经营诊断、目标达成、利润 / 成本 / 效率、经营健康度、复盘闭环。

**优先展示的 Evidence**：目标 / 预算 / 指标 → 经营诊断 → 改善机制 → 复盘闭环。

**不应强行补的内容**：把“常规周报 / 单次取数”写成“经营体系”；把“跟踪指标”写成“改善经营结果”。

---

### D｜业务策略 / 策略运营

**优先寻找的 Hiring Signals**：具体杠杆设计（定价 / 流量 / 供给 / 补贴 / 商品 / 商户 / 销售 / 履约）、策略推行、效果验证、迭代。

**优先展示的 Evidence**：掌握明确杠杆 → 策略 / 规则设计 → 协调上线 → 效果测量 → 迭代。

**不应强行补的内容**：只执行现有活动 / SOP 却写成“制定策略”；把“参与项目”写成“对业务结果负责”。

---

## 4. 责任深度校准（L0–L8）

> 深度模型完整定义、各子族强证据阈值与示例见依据层 §3。本层只给校准规则。

| Level | 执行层处理方式 |
|---|---|
| L0 信息整理 | 搜集资料、汇总报表；尚不能证明分析能力 |
| L1 分析执行 | 按既定口径拉数、调研、跑分析；证明工具 / 执行能力 |
| L2 独立分析 | 独立完成一个明确问题的分析；初步分析能力 |
| L3 问题诊断 | 构建框架、识别根因 / 机会；商业分析的重要分水岭 |
| L4 形成判断 / 策略设计 | 在不确定信息下做取舍并给出方案；战略 / 商业 / 策略岗关键高阶证据 |
| L5 推动落地 | 获得决策、协调资源、改变业务动作；从“建议者”向“业务推动者”跃迁 |
| L6 结果闭环 | 观察 / 测量策略后的效果并迭代；强结果导向证据 |
| L7 目标 / 预算 / 资源责任 | 制定、拆解、滚动调整并配置资源；经营分析 / 高级策略强证据 |
| L8 跨业务 / 公司级责任 | 跨 BU 战略、组合选择、公司级机制；专家 / 负责人层能力 |

### DEPTH-01

战略分析达到 L3–L4 且真实影响决策即可很强，不应机械要求收入归因；商业分析通常在 L3 以上开始形成强信号；经营分析的强证据往往要看到 L6–L7；业务策略若只有 L2 数据执行则很弱。动词强度不得高于上述实际层级。

### DEPTH-02

实习 / 校招阶段 L0–L2 可接受；社招 1–3 年应到 L2–L3；3–5 年应到 L3–L4；5–8 年应到 L4–L5 及以上；专家 / 负责人应到 L6–L8。不得以“协助 / 参与”字样支撑高级别责任表达。校招 / 管培通道的专属校准（CAMPUS）本轮未做，暂走通用深度梯度。

## 5. Hiring Signal → Evidence 解释规则

> 完整弱 / 中 / 强矩阵见依据层 §4「招聘信号矩阵」。本层给跨接与禁止推断（选取最易误判的信号）。

| Signal | 弱证据 | 强证据 | 常见误判 |
|---|---|---|---|
| 商业洞察 | 看了数据 / 写报告 | 发现有意义的异常、根因或机会并改变决策 / 动作 | Dashboard ≠ 洞察 |
| 经营分析 | 周 / 月报 | 建立业务健康框架，连接目标、预算 / 资源、复盘和改善 | 报数 ≠ 经营分析 |
| 战略思维 | 做行业研究 | 比较不同战略选项与取舍，形成明确战略判断并影响选择 | 研究 ≠ 战略 |
| 结构化问题解决 | “负责专题分析” | 有假设树 / 关键变量 / 根因结构，模糊问题 → 框架 → 验证 → 方案 → 结果 | PPT 结构好 ≠ 问题解决 |
| 策略设计 | 提出建议 / idea | 具体到对象、规则、资源、节奏，策略可执行、获批、落地并迭代 | 建议 ≠ 策略 |
| 数据驱动 | 会 SQL / Python | 用数据验证假设并改变判断，有测量 / 实验 / 归因意识 | 工具技能 ≠ 数据驱动 |
| 商业敏感度 | 会看收入 | 同时理解收入、成本、利润和约束，做单位经济 / 投入产出取舍 | 看到金额 ≠ 商业判断 |
| 结果导向 | 团队 KPI 上涨 | 对自己负责的交付 / 杠杆有结果，干预路径清楚、个人贡献可归因 | 团队增长 ≠ 个人成果 |
| 目标管理 | 跟踪 OKR | 拆解目标、建立过程指标，制定 / 滚动调整目标并连接资源 / 激励 | 参加 OKR 会 ≠ 目标管理 |
| 跨团队推动 | 与多部门沟通 | 协调明确任务和依赖，解决冲突、争取资源、改变行动并交付 | 开会 ≠ 推动 |
| 管理层决策支持 | 向领导汇报 | 分析被用于某项决策，推荐被采纳或使管理层改变选择 | 汇报对象高级 ≠ 决策影响大 |
| Ownership | “参与项目” | 独立负责完整模块，对问题定义、关键取舍、推进和结果形成端到端责任 | 项目成员 ≠ Owner |

### EVIDENCE-01

改写时应优先提高 **强证据** 的信息密度，而不是通过形容词强化弱证据。

### EVIDENCE-02

如果只有弱证据，应保守表达；不要把语气升级成“主导 / 操盘 / 构建体系 / 显著提升”。具体动词表与叙事链见 §9（G1 上提）。

## 7. 项目选择与排序规则

### SELECT-01｜目标子族优先

项目优先级由目标子族决定，不存在“战略项目一定排第一”。

- **Target A**：重要战略问题 → 独立定义 → 外部 + 内部证据 → 明确战略取舍 → 决策影响 / 后续推进
- **Target B**：模糊重要问题 → 独立诊断 → 根因 / 机会 → 建议 → 业务采用 / 改善
- **Target C**：目标 / 预算 / 指标 / 资源 → 经营诊断 → 改善机制 → 复盘闭环
- **Target D**：掌握明确杠杆 → 策略 / 规则设计 → 协调上线 → 效果测量 → 迭代

### SELECT-02｜同一段经历按岗位重排事实

假设候选人有一段“既做经营分析又参与策略设计”的经历，Skill 不应生成一条固定表述，而应根据目标子族重排事实：

| 目标子族 | 应突出 |
|---|---|
| A 战略分析 | 战略议题 → 独立定义 → 研究 / 建模 → 取舍判断 → 影响决策 |
| B 商业分析 | 业务问题 → 框架拆解 → 根因 / 机会 → 建议 → 业务采用 |
| C 经营分析 | 目标 / 指标 → 诊断框架 → 经营问题 → 资源 / 机制调整 → 复盘 |
| D 业务策略 | 杠杆（定价 / 供给 / 流量）→ 策略 / 规则 → 上线 → 增量效果 → 迭代 |

> **不要问“这个项目叫什么”；要问“对这个目标子族而言，这个项目里的哪一组事实最有证明力”。**

### SELECT-03｜跨职能但 Title 不匹配的项目可优先

一个跨职能但 Title 不匹配的项目，只要拥有更完整的证据链，可以优先于“同岗位 Title 但只做支持工作”的项目。例如京东网络规划岗位的全流程规划、模型、实施和运营指标责任，在投供应链策略时可能强于一个只做报表的“商业分析”项目。

## 8. Bullet 改写规则

### EDIT-01｜优先写“证据链”，不要求每条塞满所有元素

推荐信息顺序：

**业务 / 用户问题 → 候选人动作 / 关键决策 → 落地 → 验证 → 结果 / 规模**

根据事实完整度选择 3–5 个最强元素，不需要机械套模板。

### EDIT-02｜结果优于职责罗列

弱：

> 负责经营分析，与团队推进经营复盘。

强：

> 针对 [业务线] 的 [经营问题]，建立 [诊断框架]，识别 [根因]，推动 [资源 / 机制调整]，复盘 [结果]。

只有原始材料支持的字段才能填入。

### EDIT-03｜装饰性标签必须附事实

“数据驱动 / 商业敏感度 / 结果导向 / 策略 / 主导 / 闭环”等若无真实决策与结果支撑，应降级或要求补证据。优先使用具体动作动词：分析、识别、诊断、拆解、设计、构建、提出、制定、推动、协同落地、优化、验证、复盘、归因、迭代。完整动词表与“有含义 vs 装饰性标签”对照见 §9（G1 上提）。

### EDIT-04｜动词必须与事实匹配

| 事实 | 合理表达 | 不应自动升级为 |
|---|---|---|
| 只做分析 | “分析、识别、发现” | “驱动、实现” |
| 给出建议 | “提出、建议” | “制定并实施” |
| 方案被采纳 | “提出并获采纳” | “推动业务增长 X%” |
| 协调实施 | “推动、协同落地” | “负责最终业务结果” |
| 直接控制杠杆并有可信测量 | “通过……推动 / 实现……” | 可在证据充分时写因果式表达 |
| 拥有明确 KPI / 目标责任 | “负责……目标 / 达成……” | 仍不能把外部 / 团队全部变化据为个人贡献 |

### EDIT-05｜指标使用真实口径

若有基线和结果，优先写：

**from X → Y / +X% / -X% / 覆盖 N 用户 / N 客户 / N 场景**

若没有数字，可使用可验证的非数字结果：上线、完成 Pilot、被业务团队采用、覆盖多个流程、建立评测 / 机制标准。

不得生成“显著提升”“大幅增长”等无法验证的结果。指标证明力与归因边界见依据层 §4。

## 9. 改写措辞透镜（G1 上提·必读）

> ⚠️ **改写前硬门**：本章（§8）所有 Bullet 改写必须先套用本节的动词分层表、装饰性标签使用条件与叙事链模板；禁止仅凭 §8 内联的短动词示例写作，也禁止跳过本节直接凭经验措辞。完整示例与来源引用见依据层 G1（按需参考）。

### 9.1 行动动词表（按证据深度分组）

动词强度必须跟随 §4 深度模型（L0–L8），不能高于候选人实际证据层级：

| 证据深度 | 英文强动词（与 JD 原文拼写一致，利于 ATS） | 中文对应动词 | 典型误用（不可自动升级） |
|---|---|---|---|
| L1–L2 分析执行 / 数据调研 | Analyzed, Assessed, Examined, Queried, Cleaned, Modeled（基础） | 分析、梳理、清洗、搭建（取数 / 模型） | 把"跑了 SQL"写成"驱动" |
| L2–L3 独立分析 / 问题诊断 | Identified, Uncovered, Diagnosed, Detected, Discovered, Segmented | 识别、定位、诊断、发现（根因 / 机会） | 把"发现相关性"写成"识别因果" |
| L3–L4 判断 / 策略设计 | Designed, Developed, Proposed, Recommended, Formulated, Structured, Built（框架 / 模型） | 设计、构建、提出、制定、结构化 | 把"做 idea"写成"完成策略设计" |
| L4–L5 推动落地 | Drove, Led, Spearheaded, Coordinated, Implemented, Rolled out, Championed | 推动、牵头、协调落地、主导推行 | 把"参与项目"写成"对业务结果负责" |
| L5–L6 结果验证 / 闭环 | Improved, Reduced, Increased, Delivered, Optimized, Validated | 提升、降低、实现、验证、优化 | 把"团队增长"写成"个人贡献增长" |
| L7 目标 / 预算 / 资源治理 | Established, Set, Decomposed, Allocated, Governed, Forecasted | 搭建（目标 / 指标）、制定 / 拆解、配置、滚动预测 | 把"参加 OKR"写成"负责目标制定" |

中英文简历都应避免以 "Responsible for / Worked on / Helped with / Assisted in / Participated in" 或中文"负责、参与、协助、支持、涉及"开头——这些词不传达任何个人贡献。当只能确认"参与 / 支持"时，至少写明具体动作与对象，而不能停在"参与 XX 项目"。

### 9.2 有含义表述 vs 装饰性标签词表

| 装饰性 / 弱标签（无上下文时不加分，甚至减分） | 有含义的等价表达（必须落到行为 + 对象 + 结果） |
|---|---|
| "数据驱动" | "用 SQL / Python 验证假设并改变判断（例：识别 22% 闲置许可，支撑续约重谈省 $340K）" |
| "商业敏感度" | "同时理解收入、成本、利润与约束，完成单位经济 / 投入产出取舍" |
| "结果导向" | "对自己负责的杠杆 / 交付有明确结果，且作用链可归因" |
| "Owner 意识" | "对问题定义、关键取舍、推进与结果形成端到端责任" |
| "良好的沟通 / 跨部门协作" | "解决冲突、争取资源、改变行动并交付（写明冲突 / 资源 / 交付物）" |
| "战略思维" | "在模糊议题下形成明确战略取舍并影响选择 / 规划" |
| "strong communication skills"（空泛） | "向非技术高管清晰传递结论；报告被管理层用于 X 决策" |

原则：标签词只有在简历正文已有对应行为证据时才可在总结 / 技能栏复用；否则应删去标签、保留证据句。

### 9.3 叙事链模板（按子类型 A / B / C / D）

每条项目 Bullet 建议按"对象—动作—证据—结果"压缩成一个完整故事，不同子类型的逻辑落点不同：

- **A 战略分析**：`模糊战略议题 → 独立定义问题 → 外部研究 + 内部事实 + 建模 → 明确战略取舍判断 → 影响决策 / 规划 / 战略项目`。骨架："针对 [赛道 / 市场]，独立搭建 [分析框架]，综合 [内外部证据] 形成 [取舍判断]，被 [决策者] 用于 [战略选项 / 规划]。"
- **B 商业分析**：`业务异常 / 机会 → 假设树 / 分析框架 → 根因或机会 → 可执行建议 → 业务采用 / 改善`。骨架："针对 [业务问题]，以 [框架] 拆解，识别 [根因 / 机会]，提出 [建议]，业务据此 [动作]，带来 [指标变化]。"
- **C 经营分析**：`目标 / 预算 / 指标 → 经营诊断与指标体系 → 改善机制 → 复盘闭环`。骨架："负责 [业务线] 的 [目标 / 指标体系]，建立 [诊断框架]，识别 [经营问题]，推动 [资源 / 机制调整]，复盘 [结果]。"
- **D 业务策略**：`明确杠杆 → 策略 / 规则设计 → 协调上线 → 效果测量 → 迭代`。骨架："针对 [杠杆，如定价 / 供给 / 流量]，设计 [策略 / 规则]，协调 [相关方] 上线，测量 [增量效果]，迭代 [版本]。"

四类都不允许把"搭建 Dashboard / 写周报 / 做行业资料搜集"当成终点；它们只能是叙事链中的"分析执行"环节，真正的简历价值在更靠后的判断、决策或结果节点。

## 11. JD 定制流程

下游 Skill 在有目标 JD 时，建议按以下顺序处理。

### STEP 1｜分类

将 JD 分类为 A / B / C / D，可允许主类 + 次类（混合标签）。

例如：

`Primary = D`
`Secondary = C`

### STEP 2｜提取 JD Signals

从 JD 提取：

- Must
- Common
- Preferred
- 责任深度
- KPI / 结果对象
- 用户 / 客户类型
- 行业 / 商业模式
- 国家 / 区域（国际化 / 海外岗）

### STEP 3｜抽取候选人 Evidence

使用第 6 节 Schema，只记录明确事实。

### STEP 4｜建立匹配表

```yaml
signal_match:
  - signal: "经营分析"
    evidence: "候选人原项目事实"
    strength: "strong | medium | weak | none"
  - signal: "策略设计"
    evidence: ""
    strength: "none"
```

### STEP 5｜决定项目优先级

优先展示：与目标 JD 高相关；Evidence 强；Candidate Ownership 清楚；有结果或验证闭环的项目。

### STEP 6｜改写

执行第 8 节规则。

### STEP 7｜真实性 QA

检查是否出现：

- 新增不存在的能力 / 数字；
- Ownership 升级；
- 参与写成主导；
- 研究写成战略；
- 团队增长写成个人贡献；
- 工具技能（SQL）写成商业洞察；
- 留学 / 英语写成海外商分能力；
- 未经 `profile.md` 记载的语言能力表述（任何形式的，一律禁止）；
- 降低质量 / 体验未被验证的“降本”写成净价值。

若出现，回退。

## 13. 研究缺口（执行层视角）

本研究自身已明确存在以下缺口，Skill 不应自行补齐：

1. 校招 / 管培 / 储备通道（G3）专属信号本轮未做，遇该类 JD 应单独检索，不套社招规则；
2. 部分招聘页为镜像 / 第三方（L3），需按来源分级，不升级为官方原文；
3. JD 只能证明招聘期望，不能证明公司内部真实权力结构（预算签批 / P&L 权限需谨慎推断）；
4. 单公司稳定结论需 ≥5 个可比岗位或充分官方 JD；样本不足的公司只给“应提高权重的信号”，不构成“该公司比别家更偏好 X”的强结论（见依据层 G2 边界说明）。

## 14. 最短决策规则

> **先看目标 JD 属 A / B / C / D 哪类，再从候选人事实中找对应 Hiring Signal 的强 Evidence。**

> **候选人事实决定能不能写；目标 JD 决定优先写什么；本文档决定什么通常算强证据。**

> **商分 / 策略简历不是分析名词越多越好，而是“问题 → 判断 / 决策 → 动作 → 验证 → 结果”越完整越好。**

> **任何缺失的能力、指标、Ownership、结果都不得自动补写。**
