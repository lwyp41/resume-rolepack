# 互联网产品（非 AI）：证据与表达依据（依据层）

**怎么用**：执行层 `internet-product-执行规范.md` 必读；本文件**按需读** —— 拿不准某条证据算不算强证据、担心过度声称、需要措辞/动词/改写示例时再来查。

本文件不是候选人事实来源。**市场上常见的能力不等于候选人具备**；不得因为市场常见就给候选人补写 0→1、增长结果、商业化、平台架构、客户续费之类内容。

## 0. 适用域警告

- §1–§7 为**通用产品写作透镜**，源自海外公开 JD 样本（Anthropic / Figma / Stripe / Asana 等）与产品实践资料，并经本项目的海外 12 JD 样本（`_archive/ai-product-internet-product.md`）结构归纳。**只取「证据怎么组织、什么算过度声称」这类通用写法**；其对职级、技术栈、薪酬的市场要求不套用到国内岗位。
- §8 是字节/腾讯/美团/阿里钉钉/滴滴/小红书/快手/拼多多等官方 JD 及公开招聘聚合的国内研究结论，适用于国内互联网产品岗位。投金融、国企、银行时，**仍以目标雇主的调研信号（外部调研 R1–R3）为准**，本文件只提供证据组织方式。
- 本文件覆盖「互联网产品非 AI」。AI 类岗位（Agent / AI 应用 / AI 运营等）单独归 `ai-证据依据.md`，不应混用。

## 1. 招聘方反复要看的五类证据

### A. 问题与用户/客户理解

说清为谁解决什么重复性问题、用了什么证据（访谈/行为数据/竞品/桌面）、如何框定问题。

- 弱：`收集用户需求，支持产品开发。`
- 强：`通过 [访谈/行为数据/竞品]，定位 [用户/业务问题]，并据此做 [优先级/产品决策]。`

不要把内部请求或桌面研究写成用户研究；准确命名证据类型。

### B. 产品判断与优先级

让决策可见：优先了什么、推迟了什么、做了什么权衡、为什么。强信号包括路线图 ownership、机会排序、MVP 范围、build-vs-buy、在信息不全下的取舍。

- 弱：`负责产品需求，协调开发。`
- 强：`基于 [业务战略/价值矩阵]，对 [N 项需求] 做优先级排序，聚焦 [高 ROI 模块]，上线后 [释放人力/提升指标]。`

不要把路线图/PRD 本身当结果，要说明它促成了什么决策或结果。

### C. 跨职能产品交付

产品工作在研发、设计、数据、研究、运营、市场、销售、算法、客户、生态之间。bullet 应展示候选人在对齐各方围绕决策或交付结果中的角色。

- 弱：`与跨职能团队协作。`
- 强：`对齐 [具体团队]，围绕 [决策/约束/依赖]，推动 [交付物] 落地并取得 [结果]。`

### D. 交付与可衡量结果

展示从发现/定义到原型、试点、上线、采用、迭代的路径；按子族选正确层级的结果：

- P1 用户产品：激活、采用、留存、转化、参与、任务成功、满意度、GMV；
- P2 增长：拉新、激活、漏斗转化、留存、复购、变现、实验 lift；
- P3 平台：开发者采用、API 调用、可靠性、接入周期、复用率、跨产品复用；
- P4 企业：试点→推广、工作流采用、time-to-value、扩展、治理、ROI、续费/NRR。

> 禁止：没有基线、结果或业务范围，就把过程量（访谈数、功能数、活动场次）写成业务影响。

### E. 增长、采用、留存与商业化

按目标子族强调对应结果函数；不要把「做了增长活动」自动等同「对 DAU/GMV 负责」。

- 弱：`负责用户增长，组织活动。`
- 强：`针对 [漏斗阶段]，设计 [增长机制/激励/玩法]，通过 [实验/数据] 验证，改善 [拉新/留存/复购/ROI]。`

## 2. 产品证据阶梯（六层）

1. **问题定义**：用户/业务真正的问题是什么、为谁。
2. **洞察与证据**：用什么证据（研究/数据/竞品）理解问题与机会。
3. **产品决策与权衡**：做了什么优先级/范围/MVP/取舍决策。
4. **跨职能交付**：能否推动设计/研发/数据/算法/运营落地。
5. **结果与验证**：是否有指标、实验、采用或业务结果。
6. **迭代与规模化**：是否从单点复制到多场景/多客户/大规模并形成机制。

不是每个岗位都要占满六层 —— 只用 JD 与素材支撑得住的维度。

## 3. 有含义的表述 vs 装饰性标签

> 本节与 §5（叙事链）、§6（动词表）、§7（低价值表达）的写作透镜核心已上提至 `internet-product-执行规范.md`「改写措辞透镜」专节（改写前必读）。执行层为准，本节保留完整示例与补充。

**可以写（仅在能解释底层工作时）**：用户洞察、需求优先级、MVP、A/B 测试、漏斗分析、归因、用户分层、增长玩法/激励、API/SDK/能力治理、开发者体验、平台复用、GTM、定价、客户成功、续费/ROI、合规（SSO/RBAC/数据驻留）、数据看板。

**禁止当装饰标签贴**：`数据驱动`、`用户中心`、`增长黑客`、`平台生态`、`商业化`、`端到端产品生命周期`、`owner`、没有实验与结果的 `A/B 测试`、没有结果的 `GMV/DAU 增长`。

> 提醒：方法论名词（如 A/B 测试、RARRA）不是能力本身，只有当候选人真的设计/解读了实验或增长闭环时才是证据。

## 4. 与相邻岗位的边界（过度声称红线）

| 素材里的事实 | 可信说法 | 不要声称 |
|---|---|---|
| 需求/干系人收集 | 浮现并结构化了用户或业务问题；有决策证据时说「影响了优先级」 | 没有决策证据却说「负责产品策略」 |
| 项目协调 | 推动了跨职能交付、依赖或上线工作 | 没有证据却说「负责路线图/用户结果」 |
| 研究/分析 | 产出了影响产品决策的证据 | 只是桌面或市场研究，却说是「产品发现」 |
| 运营/活动 | 为特定用户群设计或改进了增长/运营机制并度量价值 | 内部流程/单次活动说成「增长体系/产品上线」 |
| 工程/实现 | 配合技术约束、交付了能力、改进了系统质量 | 仅凭实现声称产品 ownership |
| 营销/GTM/客户工作 | 把市场/客户洞察转成定位、采用、上线或反馈 | 没有产品决策却把商业执行写成产品管理 |
| 设计/体验 | 定义了交互与体验标准并验证 | 没有结果却说「主导体验战略」 |

混合型岗位用**两段式**：`用户/业务结果 + 产品机制`。不要把真实重心藏在「产品」这个大词后面。

---

## 5. 叙事链（按子族选）

- **P1 核心用户产品**：`用户/业务问题 → 用户洞察/证据 → 产品决策或权衡 → 跨职能交付 → 体验/转化结果`
- **P2 增长产品**：`增长问题/漏斗瓶颈 → 增长机制/玩法设计 → 实验/数据验证 → 采用/转化结果 → 可复用能力沉淀`
- **P3 平台/开发者产品**：`场景痛点 → 平台抽象/能力设计 → API/SDK/治理 → 开发者效率指标 → 复用/生态`
- **P4 企业/B2B**：`客户/业务问题 → 需求共创/方案 → GTM/商业化 → 交付/上线 → 采用/续费/ROI`

最强经历的第一条通常先立住「问题 + ownership + 结果」，不要以通用职责开头；完整链路可以跨几条 bullet 铺开。

## 6. 动词表（按证据类型选词）

- 发现与框定：identified / investigated / synthesized / diagnosed / framed / validated
- 产品判断：defined / prioritized / sequenced / scoped / traded off / shaped
- 交付：prototyped / piloted / launched / shipped / instrumented / integrated / scaled
- 结果：improved / increased / reduced / accelerated / expanded / retained / enabled
- 增长/采用：activated / acquired / retained / converted / adopted / expanded
- 平台/生态：abstracted / standardized / enabled / generalized / exposed
- 商业化/客户：commercialized / priced / positioned / onboarded / renewed

用与事实匹配的动词。`owned / 负责` 意味着真正的决策责任，不只是参与。

---

## 7. 低价值表达与关键词用法

**不要过度使用**：没有决策或结果的「负责」；没说决策/约束/结果的「跨职能协作」；没展示阶段的「端到端产品生命周期」；没有证据的「用户中心」「数据驱动」；只有执行却说「负责策略」；站会/迭代等流程仪式语言（除非 JD 明确看重）；把原始产出数量当成果；没有证明的软技能形容词。

**ATS 与业务语言**：只在与候选人证据匹配时使用 JD 原词；放进有证据承载的句子里，分布在经历、项目、技能中；**不要堆关键词块**，也不要列工具而不说明用它做到了什么。

**层级信号（仅作参考）**：校招/初级看问题拆解、分析可靠、研究质量、原型、需求清晰、有度量的结果、在既定范围内的执行力；正式 PM 及以上才谈领域 ownership、优先级决策、跨职能上线、可量化结果。**不得把「参与」改成「负责」来抬高层级。**

## 8. 附：国内样本研究结论

以下内容来自 2026-09-25 对字节、腾讯、美团、阿里钉钉、滴滴、小红书、快手、拼多多等官方招聘页及公开招聘聚合（如猎聘、BOSS、牛企直聘、Liepin、Quanzhi、Weekday、iimjobs、Jobted、NextLeap 等）的产品经理 JD 归纳，适用于国内互联网产品岗位，用于事实追溯与边界校验。原始 JD 样本清单未并入本文件，需按公司+岗位名追溯时查上文来源平台。

### 证据标签

**【事实】**：JD 或官方招聘资料直接出现。  
**【研究归纳】**：在多个 JD 中反复出现后形成的招聘模式。  
**【推论】**：基于上述事实对简历筛选、能力信号进行的合理解释，不等同于招聘方原话。

### 执行摘要

#### 最重要的研究结论

**第一，国内「产品 PM」按工作对象分为四类，比岗位标题更可靠。** JD 反复显示：P1 核心用户产品（抖音精选、美团非餐品类、小红书店铺/多端、拼多多 C 端、腾讯社区）、P2 增长（滴滴/美团/快手/小红书/拼多多增长）、P3 平台开发者（字节网管平台/基础平台、腾讯云 CloudBase、小米平台、钉钉标注平台）、P4 企业 B2B/SaaS（腾讯海外营销云、钉钉专业版、海外 B2B SaaS）。【研究归纳】

**第二，「从接需求到定价值」是区分初级与中高级的分水岭。** 多个 JD 与面试官反馈一致：只写「根据业务方需求完成功能」会被视为「需求翻译机」；大厂要的是需求的过滤网与价值判断者，能砍伪需求、做优先级决策。【事实+研究归纳】（来源：字节产品职责描述；才聚/一线面试官反馈）

**第三，「上线不是结束」——全生命周期与数据迭代是硬要求。** 大厂拥有海量用户数据与成熟 A/B 平台，JD 普遍要求上线后看留存/转化/LTV 并迭代，而非停在「产品上线」。【事实+研究归纳】（来源：字节/美团/小红书/拼多多 JD；才聚）

**第四，增长岗看「完整闭环 + 可复用能力」，不是单次活动。** 滴滴/美团/快手/小红书/拼多多的增长 JD 反复出现：拉新→激活→留存→复购全链路、裂变/激励/玩法、A/B 与漏斗、把一次性活动沉淀为可配置可复用可规模化的产品能力、对增长指标 owner 负责。【事实】（来源：滴滴用户增长 JD、美团提频/用增 JD、快手买家增长 JD、小红书内容种草 JD、拼多多 C 端营销/交易 JD）

**第五，平台岗看抽象能力与开发者效率，不是功能交付。** 字节网管平台、腾讯云 CloudBase、小米平台、钉钉标注平台 JD 强调：从具体场景抽象通用能力/数据模型、API/SDK/CLI/Webhook 能力治理（注册/版本/权限/审计）、开发者体验指标（接入周期/调用成功率/活跃开发者/复用率）。【事实】（来源：字节网管平台 JD、腾讯云 CloudBase JD、小米平台 JD、钉钉标注平台 JD）

**第六，B2B/SaaS 看客户共创、商业化与续费，不是仅功能上线。** 腾讯海外营销云、钉钉专业版、海外 B2B SaaS JD 强调：客户共创、PRD/用户故事/验收标准、GTM 与定价、售前/客户成功协作、ARR/NRR/续费、合规（GDPR/SSO/RBAC/数据驻留）。【事实】（来源：腾讯海外营销云 JD、钉钉专业版 JD、iimjobs/Jobted/NextLeap B2B SaaS JD、腾讯 WorkBuddy Enterprise）

**第七，最值得写的是「改变了哪段真实 workflow/链路，以及最终可测结果」。** 招聘信号弱到强大致：过程动作 → 功能上线 → 实验/数据验证 → 用户采用 → 业务结果 → 规模化/可复用。【研究归纳】

**第八，非技术/商科背景不被产品岗排除，但风险是「看起来懂业务却落不了地」。** 商科/运营/内容背景在 P1/P2/P4 有自然迁移；风险组合是「大量战略/运营语言 + 没有真实产品落地 + 没有数据/结果」。【研究归纳】（来源：钉钉专业版、美团/小红书 C 端 JD 对数据/落地的强调）

### 四类岗位画像

**P1 核心用户产品**

【事实】典型岗位：抖音精选用户产品、美团非餐品类用户产品（Keeta）、小红书店铺/多端/电商 C 端、拼多多 C 端、腾讯 Content & Community、快手导购/商城。核心是对用户路径/交易链路/体验负责，强调用户洞察、数据驱动（漏斗/路径分析）、跨职能交付、体验与转化结果（转化率/GMV/留存）。【事实】（来源：字节抖音精选 JD、美团非餐品类 JD、小红书店铺用户产品 JD、拼多多 C 端 JD、腾讯社区 JD、快手导购 JD）

**P2 增长产品**

【事实】典型岗位：滴滴用户增长、美团用增/提频（Keeta）、快手买家增长（电商）、小红书内容种草/增长、拼多多 C 端营销/交易/平台增长。核心是拉新/激活/留存/复购/转化闭环，增长玩法（裂变/激励/任务/补贴）、A/B 与漏斗、对增长指标 owner 负责、活动→可复用产品能力沉淀。【事实】（来源：滴滴增长 JD、美团提频/用增 JD、快手买家增长 JD、小红书内容种草 JD、拼多多营销/交易/平台增长 JD）

**P3 平台/开发者产品**

【事实】典型岗位：字节网管平台（开发者方向）、字节基础平台（抖音）、腾讯云 CloudBase、小米平台、钉钉标注平台。核心是平台抽象、开发者体验、API/SDK/能力治理、可复用底座、开发者效率指标；技术理解是协同研发的关键而非本人编码。【事实】（来源：字节网管/基础平台 JD、腾讯云 CloudBase JD、小米平台 JD、钉钉标注平台 JD）

**P4 企业/B2B SaaS**

【事实】典型岗位：腾讯海外营销云、钉钉专业版、海外 B2B SaaS（POS/Retail/CRM/ERP）、腾讯 WorkBuddy Enterprise。核心是客户共创、企业需求→可落地方案、GTM/定价、客户成功（签约/上线/续费）、合规与安全；商业指标（ARR/NRR/续费）。【事实】（来源：腾讯海外营销云 JD、钉钉专业版 JD、iimjobs/Jobted/NextLeap B2B SaaS JD、腾讯 WorkBuddy Enterprise JD）

### 招聘方认可的结果指标

**P1 用户产品**：激活、采用、留存、转化、参与度、任务成功、满意度、GMV。  
**P2 增长产品**：拉新、激活、漏斗转化、留存、复购、变现、实验 lift、裂变系数、ROI。  
**P3 平台产品**：开发者采用、API 调用、可靠性、接入周期、复用率、跨产品复用。  
**P4 企业产品**：试点→推广、工作流采用、time-to-value、扩展、治理、ROI、续费/NRR。

Resume Skill 不应自动要求每个项目都写 GMV/DAU/ARR；应匹配岗位真正的结果函数。

---

### 高价值简历证据

最重要原则：

> **能力词不是 Evidence；动作也不是最终 Evidence；完整闭环事实才是 Evidence。**

例如「熟悉增长」只能证明声明；「做过增长活动」证明一定 hands-on；「设计用户分层+激励体系→做 A/B→分析裂变系数与首单转化→沉淀为可配置模板并被多场景复用」才同时证明 增长机制 + 数据验证 + 产品抽象 + Ownership。

对机器筛选，优先抽取这些事实：
- **0→1**：是否从问题定义推进到 MVP/试点/上线，而非只维护已有功能。
- **Ownership**：是否有明确决策权或端到端责任。
- **用户/客户洞察**：是否发现具体用户/业务问题并验证。
- **数据驱动**：是否用数据发现问题、设指标、实验、复盘。
- **增长/采用**：是否真有用户/客户开始使用并持续使用。
- **平台复用**：是否把场景抽象为通用能力并实际被复用。
- **商业化/客户成功**：是否产生营收、续费、ROI。
- **Scale**：是否从单点复制到多场景/多客户/大规模。

### 公司层面招聘信号

**字节**：样本横跨抖音用户/内容、基础平台、网管开发者平台，既重用户体验与数据迭代，也重平台抽象与 AI 内容理解（基础平台 JD 提到 Workflow/Agent 框架/模型评测）。【事实】

**腾讯**：样本含社区、海外营销云、云 CloudBase、QQ-Agent 等；云与海外方向明显提高 商业化/GTM/合规/开发者生态 权重；Agent 方向属 AI 族，本依据层不覆盖。【事实】

**美团**：用户增长（提频/用增）、非餐品类用户产品（Keeta）并重，强交易与海外增长信号；明确要求数据驱动与 AI 工具辅助提效（作为效率手段，不是 AI 岗）。【事实】

**阿里/钉钉**：钉钉专业版（商业化协同办公）、标注平台（AI 数据产品）显示强 B2B/平台信号；钉钉专业版明确要求 ownership 与商业结果。【事实】

**滴滴**：用户增长 JD 最完整地展示了增长闭环与「活动→可配置可复用能力」的产品抽象要求。【事实】

**小红书**：社区/内容/电商 C 端并重，强 内容种草+数据驱动（A1/A2 人群、LT30 次留、归因）、店铺转化与商家经营工具信号。【事实】

**快手/拼多多**：电商 C 端/买家增长/导购信号强，重 购物动线、转化效率、补贴与激励、SQL/A-B 数据推导。【事实】

### 可直接供 Resume Generation Skill 使用的规则集

| Target / 情况 | 机器应优先寻找的事实 |
|---|---|
| Target = P1 用户产品 | 用户洞察、交易/体验链路、产品决策、数据迭代、转化/留存/GMV |
| Target = P2 增长 | 增长闭环、玩法/激励、A/B/漏斗、可复用能力、ROI |
| Target = P3 平台 | 平台抽象、API/SDK/治理、开发者效率、复用率 |
| Target = P4 企业 | 客户共创、商业化/GTM、交付/续费、合规、ARR/NRR |
| 候选人写「熟悉增长/数据驱动」 | 只记作 weak skill signal |
| 候选人真实做增长闭环 | 升为 strong growth signal |
| 候选人只是参与某活动 | 不升为对增长指标负责 |
| 平台项目有真实复用 | 升为 medium/strong platform signal |
| B2B 项目有真实续费/ARR | 升为 business-impact evidence |
| 非技术候选人只有课程/证书 | 不视为已补足产品深度 |
| JD 未要求商业化/续费 | 不应为了 B2B 标签强行突出 |
| 项目只是使用 AI 工具提效 | 可证明效率，不证明 AI 产品 ownership |
| 项目没有实验/数据 | 不得自动生成「建立实验/数据体系」等表述 |
| 项目没有上线或用户 | 不得将方案写成 production 产品 |

## 9. 附：子族识别参考（轻量）

> 本依据层不含完整分类器（分类与判定属执行层职责）。以下仅为信号提示，正式判定请回 `internet-product-执行规范.md` §2。

| 子族 | 高频信号（看核心交付物，不看标题） | 典型结果对象 |
|---|---|---|
| P1 核心用户产品 | 用户功能、交易链路、社区/内容、端到端体验 | 体验、活跃、留存、转化、GMV |
| P2 增长产品 | 拉新/激活/留存/裂变、漏斗、A/B、增长玩法 | DAU/MAU、复购、ROI |

| P4 企业/B2B | 企业客户、SaaS、商业化、GTM、续费、合规 | ARR、NRR、客户采用、ROI |
