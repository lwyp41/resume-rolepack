# 简历 DOCX 排版规范（项目默认）

> **自动应用规则：在本项目中，任何简历修改、重排、重写或生成 Word 前，都必须解析 active format contract。优先使用用户在当次请求中明确指定的版式，其次使用已批准的 `.givemejob/formats/` 格式，再使用本文件，最后使用 givemejob Skill 内置格式。若本文件适用，必须先读取并应用本文件；不得沿用旧脚本、旧产物或旧对话中的排版。**
>
> 本文件替代此前使用蓝色标题、1.2 倍行距、10pt 正文和 8300 DXA Tab Stop 的旧规范。`#548DD4`、720 DXA 页边距、10pt 正文、1.2 倍行距和 8300 DXA 日期 Tab 均为过期规则，不得继续使用。

## 一、格式来源与锁定信息

- 参考文件：**不在此硬编码**。取 `profile.md` → `protected_originals` 中标了 `format_baseline: true` 的那一份；若无人标记，取列表第一份。
- 文件 SHA-256：同上，从 `profile.md` 读取。**profile 未记录时必须当场计算并回填**，不得沿用本文件里的任何历史值。
- 提取日期：`（由本次提取时填写）`
- 页数：`1`
- **注意：上面的页数只是参考文件当时的页数，不是生成目标。** 产出 2 页是正常结果，
  不得为压缩页数删除有事实支撑的内容。篇幅原则见
  `RESUME_OPTIMIZATION_INSTRUCTIONS.md`，多页排版规则见本文件第十六节。
- 节数：`1`
- 页面：A4 纵向
- 参考文件为受保护的原始文件，只读，不得修改、覆盖、重命名或移动。
- 如果参考文件 SHA-256 发生变化，必须重新提取并核对本规范，不得直接把新内容套入旧参数。

## 二、生成与输出规则

1. 修改或生成前，先读取 active format contract、`RESUME_OPTIMIZATION_INSTRUCTIONS.md` 和所需素材文件；本文件是当前项目的 active format contract 时，必须完整读取。
2. 所有新简历输出到 `生成简历/`。
3. 文件名为 `简历_<公司名>_<岗位名>_v<版本号>.docx`，同岗位递增版本号，不覆盖旧版本。
4. QA 渲染、临时文件和脚本默认放入每次运行独立的系统临时目录，并在验证完成后自动清理。只有用户明确要求保留，或为调试显式启用保留选项时，才放入 `生成简历/.qa/`。
5. 所有文字必须是可选中、可复制的真实文本。
6. 除用户明确要求改变版式外，本规范为默认视觉权威。

## 四、字体、颜色与行距

### 字体

- 所有可见文字：微软雅黑。
- OOXML 中 `ascii`、`eastAsia`、`hAnsi`、`cs` 均设为 `微软雅黑`。
- Node.js `docx` 中使用 `font: "Microsoft YaHei"`。
- 不混用宋体、Calibri、Arial 或其他字体。

### 颜色

- 姓名、联系方式、板块标题、公司名、岗位名、正文、日期、项目符号统一为黑色 `#000000`。
- 日期不是灰色，不改用 `#666666`。
- 不使用蓝色、主题色或渐变。
- 不使用文字高亮、底纹或彩色标签。
- 唯一的装饰线是板块标题下方黑色细线。

### 行距

- 源文件没有显式设置行距，使用 Word 单倍行距。
- 使用 `docx` 库时，正文保持单倍行距，可使用 `line: 240, lineRule: "auto"`。
- 不得使用旧规范的 `line: 288`、1.2 倍行距或类似的额外放大行距。
- 不额外设置固定行高，避免裁切微软雅黑的上下伸部。

## 八、公司、项目和教育行

### 公司、项目行

使用同一个 Paragraph，左边放公司或项目名称，中间插入 `\t`，右边放日期：

```text
公司或项目名称	YYYY.MM－YYYY.MM
```

- 公司或项目名称：9pt 加粗
- 日期：8pt 加粗
- Tab Stop：`RIGHT`，位置 `9638`
- 日期格式：`YYYY.MM－YYYY.MM`，保留源文件使用全角连接符 `－`
- 不得拆成两个独立段落
- 不得使用表格、文本框或左右浮动对象实现公司行

### 岗位、学位或方向行

使用同一个 Paragraph，左边放岗位或学位信息，右边放行业、方向或补充标签：

```text
岗位、学位或方向	行业或补充标签
```

- 全部文字：8pt 加粗
- Tab Stop：`RIGHT`，位置 `9638`
- 不得加项目符号

### 教育经历行

源文件用了一个无边框的 3 列表格：

| 项目 | 精确值 |
|---|---|
| 表格总宽 | `9638` DXA |
| 三列宽度 | `3600 / 3638 / 2400` DXA |
| 表格边框 | 全部 `none` |
| 单元格边框 | 全部 `nil` |
| 单元格上下边距 | 各 `18` DXA |
| 前两列右边距 | 各 `70` DXA |
| 日期列右边距 | `0` DXA |

源文件的可见位置为：

- 学校从正文左边缘开始，`x=56.64pt`
- 学位从约 `x=236.69pt` 开始，对应第二列起点 `3600` DXA
- 日期右边缘为 `x=538.58pt`，对应 `9638` DXA

**ATS 安全实现要求：**

后续生成简历时，不复制真实表格结构。每条教育记录改成一个 Paragraph，使用两个 Tab Stop 复现三列视觉：

```javascript
tabStops: [
  { type: TabStopType.LEFT, position: 3600 },
  { type: TabStopType.RIGHT, position: 9638 },
]
```

文本结构：

```text
学校	学位或专业	日期
```

第一行学校、学位常规 8pt，日期加粗 8pt。第二行全部加粗 8pt。这样既保留源文件的对齐效果，又避免表格降低 ATS 解析稳定性。

如果学校或学位过长，允许在各自语义区间内自然换行。不得缩小字号、压缩字距、截断文字或让日期覆盖正文。

## 九、项目符号

职责与成果条目使用原生 Word bullet：

- 段落样式：`List Paragraph`
- 编号定义：`numId=1`，`abstractNumId=0`，`ilvl=0`
- 符号：`•`，Unicode `U+2022`
- 左缩进：`290` DXA
- 悬挂缩进：`200` DXA
- 正文文字起点：`290` DXA
- 项目符号起点：`90` DXA
- 所有条目文字：8pt
- 每条开头的语义标签加粗，例如“竞争格局研究：”“数据与方法：”
- 条目之间不额外增加段前、段后间距

推荐写法：

```javascript
new Paragraph({
  bullet: { level: 0 },
  indent: { left: 290, hanging: 200 },
  spacing: { before: 0, after: 0 },
  children: [
    new TextRun({ text: "标签：", bold: true, size: 16, font: "Microsoft YaHei", color: "000000" }),
    new TextRun({ text: "正文。", bold: false, size: 16, font: "Microsoft YaHei", color: "000000" }),
  ],
})
```

严禁：

- 在标题、公司行、教育行、岗位行上添加 bullet
- 手工输入 `•` 来代替原生项目符号
- 使用 `◆`、`★`、`▶` 等异形符号
- 使用表格承载长段经历条目

### 生成器默认值陷阱（docx 9.x）

`docx` 库的内置项目符号与本节要求不一致，直接沿用会静默产出不合规文件：

| 项目 | `bullet: { level: 0 }` 默认值 | 本节要求 |
|---|---|---|
| 符号 | `●` U+25CF | `•` U+2022 |
| 缩进 | `720 / 360` DXA | `290 / 200` DXA |
| 编号引用 | 指向库内置定义 `abstractNumId=1` | `abstractNumId=0`、`numId=1` |

因此必须显式声明编号定义，禁止使用 `bullet: { level: 0 }`：

```javascript
numbering: {
  config: [{
    reference: "resume-bullet",
    levels: [{
      level: 0,
      format: LevelFormat.BULLET,
      text: "\u2022",
      alignment: AlignmentType.START,
      style: {
        paragraph: { indent: { left: 290, hanging: 200 } },
        run: { font: "Microsoft YaHei", size: 16, color: "000000" },
      },
    }],
  }],
}
```

条目段落改用 `numbering: { reference: "resume-bullet", level: 0 }`，并保留段落级 `indent: { left: 290, hanging: 200 }`。

库仍会把内置定义一并写进 `numbering.xml`，使自定义编号落到 `abstractNumId=2` / `numId=2`。生成后必须用 `scripts/normalize-numbering.py` 归一化：只保留自定义定义，`abstractNumId` 改为 `0`、`numId` 改为 `1`，并同步 `document.xml` 中的 `w:numId`。

```powershell
python <SKILL_DIR>/scripts/normalize-numbering.py <输入.docx> <输出.docx>
```

运行约束：

- 仅依赖 Python 标准库（`zipfile`），**无需 `pip install`**，任意工作目录下可直接运行。
- 之所以用 Python 而非 Node：早期版本是 ESM 脚本，bare import 从**脚本自身所在目录**向上查找
  `node_modules`（与 cwd 无关），而 skill 安装目录下没有 `node_modules`，安装态必然报
  `ERR_MODULE_NOT_FOUND`。零依赖的 Python 版彻底规避了这类问题。
- 生成 DOCX 本体若用 Node 的 `docx` 包，仍需 `npm install docx`；网络不通时换可达的镜像源。
  但**编号归一化这一步不依赖它**。
最终是否达标以第十四节的检查为准；`scripts/qa-resume.ps1` 因本机 PowerShell 执行策略为
Restricted 而无法直接调用，QA 走环境替代路径（见 `AGENTS.md` 的环境实测章节）。

## 十一、ATS 硬性规则

视觉规范与 ATS 解析冲突时，优先保证 ATS 可解析：

1. 禁止用文本框承载正文。
2. 禁止用图片或图标承载文字。
3. 禁止分栏。
4. 教育信息不生成真实表格，使用单 Paragraph 和两个 Tab Stop 复现视觉对齐。
5. 页眉页脚不放关键信息。
6. 手机号使用连续数字，不加空格或横线。
7. 邮箱保持标准完整格式。
8. 板块标题使用标准名称：`教育经历`、`实习经历`、`工作经历`、`项目经历`、`专业技能`、`语言能力` 等。
9. 标题独占一行。
10. 所有正文均为真实文本。
11. 所有关键词自然写入句子，不堆砌。

参考文件的正文顺序为：

## 十三、特殊字符

- 所有文字直接写入 `TextRun`，不做 `JSON.stringify`、`encodeURI` 或手动转义。
- 中文引号 `「」『』`、书名号 `《》`、括号 `【】`、百分号 `%`、全角竖线 `｜` 和全角连接符 `－` 可直接写入。
- 日期连接符按参考文件使用全角 `－`，不要改成半角连字符、短横线或长横线。
- 如果素材本身包含反引号，生成前替换为全角反引号 `｀`，避免破坏脚本字符串。

## 十四、交付前验证

每次修改或生成后，必须完成以下检查：

1. DOCX 文件成功创建，大小正常，未覆盖旧版本。
2. 页数、分节、A4 页面和边距与本规范一致。
3. 全文为微软雅黑，正文条目为 8pt，公司或项目名称行为 9pt 加粗。
4. 所有文字和日期为黑色，没有旧蓝色标题或灰色日期。
5. 日期右边缘统一对齐到 `9638` DXA。
6. 教育行使用 ATS 安全的 Paragraph + Tab Stop 实现，没有真实表格。
7. 项目标题、公司行、教育行、岗位行没有误加 bullet。
8. 所有实习经历仍保留，只有详略区别。
9. 使用 Word 或可靠渲染器导出 PDF，并逐页检查。
10. 逐页确认无裁切、重叠、错行、异常空白、头像遮挡和分页断裂。
11. 若渲染结果不清晰或页码异常，修正后重新渲染，不得直接交付。
12. 多页时确认板块未被跨页截断：公司行、岗位行与其首条条目同页，教育行不被拆开。
13. 多页时确认第 2 页内容充实度合理（不至于像"溢出"），详见第十六节。
14. 确认已如实报告实际页数，且没有为了页数删除有事实支撑的内容。

通过上述检查后，才可向用户交付最终 DOCX。

## 十五、QA 生命周期

- QA 中间文件包括临时输入 DOCX、PDF、PNG 渲染图、验证报告和生成脚本。
- QA 必须在交付前完成，但 QA 文件不是交付物，也不是事实来源。
- 默认流程：创建临时目录 → 生成并验证 → 渲染并检查 → 将通过检查的 DOCX 写入 `生成简历/` → 删除临时目录。
- 如果生成或验证失败，也应在记录必要错误信息后清理临时目录；需要保留现场时，必须明确启用调试保留或经用户要求后再保留到 `生成简历/.qa/`。
- 对话交付时报告最终 DOCX 路径、实际页数和 QA 是否完成；不必保留完整 QA 文件。

## 十六、多页排版规则

本规范**不要求**简历必须是 1 页。产出 2 页是正常结果，第 2 页同样受本文件全部规则约束。

1. **内容决定页数，页数不决定内容。** 不得为了减少页数删除第十二节允许保留的板块，
   也不得删除有事实支撑的经历条目、项目或能力证据。
2. **板块不得被拦腰截断。** 若某段经历在第 1 页末尾放不下，整段移到第 2 页，
   不要把公司行留在页尾、条目甩到下一页。用 `keepNext` 保证公司行、岗位行、
   教育行与其第一条 bullet 同页。
3. **第 2 页过少时才考虑压缩。** 若第 2 页内容不足约 1/3 页，视觉上是"溢出"而非完整
   第二页，此时才按 `RESUME_OPTIMIZATION_INSTRUCTIONS.md` 的压缩顺序调整，
   并在交付说明中列出每一处删减。
